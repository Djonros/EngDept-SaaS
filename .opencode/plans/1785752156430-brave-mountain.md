# Миграция на автономную версию: SQLite без Supabase

## Решения (подтверждены пользователем)
- **Полный переход** на SQLite в master, Supabase-код удаляется
- **Сброс пароля по email отложен** — пароль пользователю сбрасывает владелец через админку
- Стек: **better-sqlite3** (без ORM), миграции = SQL-файлы с авто-применением при старте
- Auth: собственный — scrypt-хэши (node:crypto), сессии в httpOnly-cookie + таблица `sessions`
- Изоляция workspace: все запросы через repo-слой с обязательным `workspace_id` (замена RLS)
- Ключи лицензий Ed25519 **не меняются** (generate-license.bat остаётся)

## Архитектура после миграции
- `data/app.db` — SQLite (WAL), создаётся при первом запуске
- `uploads/` — логотипы, отдача через `/api/files/[...path]`
- `.env` сокращается до: `SESSION_SECRET`, `LICENSE_ENCRYPTION_KEY`, `PORT`, `TELEGRAM_BOT_TOKEN` (опц.)
- Пользовательский инсталл: распаковал → `install.bat` (проверка Node + .env) → `start.bat`. Внешних сервисов нет.

## Риски
- **better-sqlite3 в standalone**: нативный бинарь может не попасть в трейс — обязательная проверка чистого запуска dist
- **Изоляция данных**: RLS больше не страхует — чек-лист по каждому роуту: каждое чтение/запись фильтруется `workspace_id`
- Конкурентность: WAL + короткие транзакции (достаточно для малых команд)
- Dev-данные из Supabase не переносятся — тестовый воркспейс пересоздаётся; (опц.) скрипт экспорта данных клиентов из Supabase в SQLite, если появятся клиенты на старой версии
